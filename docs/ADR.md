# ADR-001：墨办（InkTask）桌面端技术架构

- 状态：已采纳（Accepted）
- 日期：2026-09-02
- 责任人：用户（本地执行 `npm run dist` 构建与验收，检查路径见「fitness functions」）

## 决策问题

为一个「Windows 本地离线、深色 UI、支持剪贴板图片内嵌、全局快捷键置顶/隐藏、按紧急程度自动排序并显示到期倒计时」的办公待办工具，选择什么客户端技术栈与数据存储方案？

## 目标 / 非目标

**目标**

1. Windows 单文件 `.exe`（NSIS 安装包 + 便携版），完全离线运行，无任何网络依赖。
2. 剪贴板图片**内嵌在任务详情里**（所见即所得），不是附件列表。
3. 全局快捷键：显示/隐藏面板、切换窗口置顶。
4. 任务按「紧急程度」自动排序（逾期置顶 + 紧急度加权 + 到期临近加权），列表项旁常驻到期倒计时。
5. 深色、精致、交互便捷的 UI。

**非目标**：多端同步（S3/网盘）、团队协作、移动端。单机单用户。

## 约束

- 用户在 Windows 上自行构建，构建门槛要低（一条 `npm run dist`）。
- 数据必须本地持久化且不能因崩溃损坏（原子写入）。
- 无签名证书，需提供免安装便携版以规避 SmartScreen/杀软误报带来的安装阻碍。

## 备选方案

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **Electron + 原生 JS（无构建步骤）+ JSON 文件存储** | ✅ 采纳 | `clipboard.readImage`/`globalShortcut`/`setAlwaysOnTop`/托盘均为内置能力，图片粘贴、热键、置顶三条核心需求零插件实现；electron-builder 一键产出 NSIS + portable；渲染层不依赖打包器，`npm start` 即可跑，排障成本低 |
| Tauri 2 + Svelte（EggDone 同款） | ❌ 否决 | 需 Rust 工具链 + WebView2 + 各插件（剪贴板图片、global-shortcut），用户侧构建门槛高；跨平台交叉编译 Windows 产物链路长、易踩坑。安装体积优势（10MB vs ~90MB）对本场景不是关键约束 |
| C# WPF / WinUI | ❌ 否决 | 原生体积小，但开发与交付（深色精致 UI、富文本+图片、打包）工作量数倍，迭代慢 |
| 纯 Web PWA | ❌ 否决 | 无法注册全局快捷键、无法置顶窗口、无法可靠读取系统剪贴板图片，核心需求不满足 |

## 决策

**Electron 桌面应用**：主进程负责窗口/托盘/全局热键/IPC/文件存储；渲染层为无构建的 HTML+CSS+JS（contextIsolation 开启，preload 暴露白名单 API）；数据存于 `%APPDATA%\inktask\`（`tasks.json` 原子写入 + `images\` 图片库 + `settings.json`）；图片经自定义 `inkimg://` 协议加载，不放宽 webSecurity。打包用 electron-builder（NSIS + portable 双产物）。

## 后果

**正面**

- 三条核心需求（剪贴板图、热键、置顶）全部走官方稳定 API，行为可预期。
- 无前端构建链：改 UI 直接改 HTML/CSS 即刻生效，用户可自行魔改。
- JSON + 图片文件存储人类可读，备份即复制文件夹；提供应用内导出/导入。

**负面**

- 安装包体积约 70–90MB、常驻内存约 100–150MB（Chromium 内核的固定成本）。
- 未签名 exe 可能被 SmartScreen 提示，需用户点「仍要运行」，或自购证书签名（已在 README 说明）。
- 富文本用 `contenteditable` + 白名单净化，需严格 sanitize 防止粘贴携带脚本。

## 可逆性

- 渲染层与主进程通过 preload 白名单 API 解耦，未来迁移 Tauri 只需重写 IPC 适配层 → **双向门**。
- 数据为版本化 JSON（`meta.version`），未来换 SQLite 只需写一次迁移 → **双向门**。
- 若日后需要多端同步，可在此 JSON 结构上叠加（EggDone 的 S3 合并模式可直接借鉴）。

## 系统图

```
┌─ 主进程 (Node) ────────────────────────────────┐
│ 窗口(frameless/置顶/隐藏)  托盘(菜单/点击)        │
│ globalShortcut(显示隐藏/置顶)  到期轮询→Notification │
│ IPC: tasks CRUD / image save / settings / export │
│ Store: tasks.json(原子写) images/*.png settings.json │
│ protocol: inkimg://img/<id>.png → 本地文件        │
└───────────────┬────────────────────────────────┘
                │ contextBridge (inktask.* 白名单)
┌───────────────┴────────────────────────────────┐
│ 渲染层 (无构建 HTML/CSS/JS)                      │
│ 快速新增 → 任务卡片(自动排序+倒计时) → 详情编辑器    │
│ 富文本: contenteditable + paste拦截 + 图片内嵌     │
│ 浏览器降级模式(localStorage+dataURL)→可独立预览    │
└────────────────────────────────────────────────┘
```

# ADR-002：重复任务（完成制复活）引擎设计

- 状态：已采纳（Accepted）
- 日期：2026-09-04（v1.4.0 打卡式 → v1.4.1 重构为完成制）

## 决策问题

「每天下班签退」「每周周报」「每月对账」这类周期性事务如何建模？重复任务的完成语义与普通任务如何统一？

## 备选方案

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **完成制复活：单任务 + 完成时推进 `dueAt` + 周期开始时复活** | ✅ 采纳 | 与普通任务交互完全一致（点完成→已完成区）；第二天任务自己回来，符合「打卡签退」直觉；无新任务生成，数据模型只加 4 个字段 |
| 推进式（v1.4.0 打卡式）：勾选即打卡、任务保持未完成 | ❌ 替换 | 勾选后任务既不进已完成区、时间又跳走，用户无法从列表看到「今天做完了」的反馈，与心智模型冲突 |
| 模板式：完成时按模板克隆新任务 | ❌ 否决 | 任务爆炸式增长、删除/重命名要级联到「未来实例」、已完成列表被每日条目淹没 |
| 日志式：记打卡事件流，dueAt 由日志推导 | ❌ 否决 | 存储与渲染都要聚合计算，浏览器降级模式（localStorage）下多余复杂 |

## 决策

`recur.js` 纯函数引擎（`normalize / nextDue / completeOccurrence / undoComplete / refresh / refreshAll`）：

1. **完成即打卡**：`completeOccurrence` 置 `completed = true` 进已完成区，同时以当前 `dueAt` 为锚点算下一次出现（保持时分秒锚点），`streak` 连击 +1；无到期时以当前时刻为锚。
2. **复活点 = 下一周期所在日的 0 点**：`refresh` 在 `now >= startOfDay(dueAt)` 时把已完成任务复活为待办（每天 18:00 的任务 → 次日 0 点回来）。触发时机三处：启动加载后、30 秒巡检、窗口 focus / visibilitychange——应用整晚没开也不丢，启动补账。`dueAt` 停留在过去日期时先逐周期对齐到「今天或之后」的第一次出现（保留时分锚点）：晚开应用（如 19 点才开、已过 18:00 到期点）也以逾期状态复活而非静默跳过当天；工作日频率不会对齐到周末。
3. **周期跳过**：`nextDue` 循环推进直到超过 now——错过多个周期只落到下一次，不补打卡。补完成逾期任务时若下一周期所在日已开始（如下午补昨天的签退），完成即立刻复活等今天这一轮。
4. **月末钳制**：每月 31 日完成 → 2 月 28/29 日，不越界。
5. **连击判定**：`lastDoneOccur` 与本次锚点间隔 ≤ 1.5 个近似周期则累计，否则归 1（近似周期：月按 30.44 天）。
6. **快照撤销**：完成返回快照，toast 5 秒撤销与「取消完成」都走 `undoComplete` 精确回滚；重启后快照丢失则按 `lastDoneOccur` 近似回退。
7. `dueAt` 为 null 的任务也可设重复（如「不定期但每 3 天一次」），首次完成时锚定当前时刻。

## 后果

- 勾选按钮语义统一：重复任务与普通任务都点勾选完成，仅在完成时多推进一个周期。
- 「清除已完成」跳过重复任务（它们下一周期还要回来），toast 说明保留数量并提供「一并清除」选项（以点击时实时状态为准，清除后仍可撤销），去留由用户决定。
- 已完成区的重复任务卡片显示「下次 …」徽章，明示它会回来。
- 备份导入导出无需感知重复语义（字段随任务 JSON 原样走），旧数据无 `recur` 字段自然兼容。
- 限制：改频率不改历史 streak；提前完成（锚点在未来）直接推进一个周期。

## fitness functions

| 不变量 | 检查 |
| --- | --- |
| 完成后 completed=true、dueAt 推进、streak 语义正确 | `npm test` → `tests/recur.test.mjs`（21 项：复活时点 / 补完成逾期 / 周期跳过 / 月末钳制 / 断档重计 / 撤销恢复） |
| 复活只在周期日开始，未跨点不复活 | `tests/recur.test.mjs`（当晚保持已完成 / 次日 0 点 / 周五→周一 / 旧数据兜底） |
| 晚开应用不跳过当天出现（过了到期点打开仍复活为逾期待办） | `tests/recur.test.mjs`（第二天 19 点打开 / 离开多日对齐到今天） |

# ADR-003：tasks.json 文档结构含分组，孤儿引用自动重建

## 决策问题

桌面版自首个版本起，渲染层 `state.doc = { meta, tasks, groups }` 在内存中是完整的，但 `tasks:save` IPC 通道只透传 `payload.tasks / payload.meta`，`groups` 字段在主进程边界被丢弃——**分组定义从未落盘**，重启即丢；任务上的 `groupId` 引用却随任务保存，形成「孤儿引用」。备份导出 / 导入、到期通知触发的保存同样丢分组。

## 决策

1. **单一文档结构**：`tasks.json = { meta, tasks, groups }`，`Store.saveTasks(tasks, meta, groups)` 落盘；groups 缺省时**保留内存现有值**（防调用点遗漏传参意外清空），显式传 `[]` 才清空（删除最后一个分组）。
2. **读入归一化**：`init()` 对旧版数据（无 groups 字段）补 `groups: []`，内存结构恒完整。
3. **全链路透传**：渲染层保存、备份导出（backup 含 groups）、备份导入（按 id 去重合并，备份定义胜出）、checkDue 落盘、数据目录迁移（整文件复制天然保留）。
4. **孤儿引用自动重建**：渲染层启动 / 外部数据采纳时，任务引用的 `groupId` 在 groups 里找不到定义 → 按引用各建一个占位分组（`分组N`），任务仍正确归堆，用户改名即完成恢复。触发点：`init()`、`adoptExternal()`、`reloadFromMain()`。

## 后果

- 旧版数据（含本缺陷期间产生的）升级后：任务带孤儿引用会自动归堆到占位分组，toast 提示改名。
- 分组定义一旦落盘，后续迁移 / 备份往返不丢。
- 删除分组时任务 `groupId` 置 null（原有行为），不产生新孤儿；删除带 5 秒撤销（恢复分组定义与任务归属，撤销窗口内被改去其他分组的任务不受影响）。

## fitness functions

| 不变量 | 检查 |
| --- | --- |
| groups 落盘往返、缺省保留、显式清空 | `npm test` → `tests/store.test.mjs`（4 项分组持久化） |
| 孤儿引用重建占位分组、任务归堆、改名落盘 | jsdom 端到端（`tests/race.test.mjs`） |

# ADR-004：主进程→渲染层数据同步的版本守卫与补丁通道

## 决策问题

渲染层保存有 **400ms 防抖窗口**，而主进程会在自己的时机改任务（到期检查 `checkDue` 每 20s 一轮、备份导入、数据目录切换）并广播 `tasks-changed` 全量文档。若广播落在防抖窗口内，`adoptExternal()` 的**整体替换**会用主进程的旧文档冲掉渲染层未落盘的编辑——用户眼睁睁看着分组归属 / 勾选 / 改名消失，随后的任意一次编辑再把被冲掉的状态持久化，**数据永久丢失**。这是「分组明明分好了又没了」的根因。

## 决策

1. **版本守卫（adoptExternal）**：以 `meta.updatedAt` 比较，外部文档不严格更新（`ext <= cur`）则拒绝采纳。渲染层每次 `persist()` 都打新的 `updatedAt`，天然区分「主进程自改」与「主进程回显旧数据」。
2. **补丁通道（tasks-patch）**：`checkDue` 不再全量广播，只发 `{ notifiedDue: [{id, notifiedDue}] }` 补丁，渲染层**原位改标志**，不做任何文档替换——主进程最高频的自改场景不再有竞态窗口。
3. **导入提升时戳**：备份导入合并落盘时 `updatedAt: Date.now()`，确保守卫把导入结果当作新数据采纳；渲染层导入前先 `Storage.flush()` 落盘本地编辑。
4. **目录切换**：`reloadFromMain()` 本就直取新数据（不经守卫），广播路径守卫跳过也不影响。

## 后果

- 防抖窗口内的编辑不再被任何主进程广播冲掉；等时戳广播视为陈旧拒绝。
- 渲染层可能短暂持有 `notifiedDue=false` 的旧副本，极端窗口下同一任务可能多提醒一次（罕见，可接受）；主进程文档始终自洽。
